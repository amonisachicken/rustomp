# 声明式构建规范（插件项目 → 多平台产物）

> 状态：**代码生成已实现**（S1a–S1d，2026-10-26）；打包按平台分仓（macOS ✅ / Windows ✅ / Linux ✅，见 §4.0 平台策略）
> 相关：`DEVLOG.md` E33 / ADR-014；`docs/component-library.md`、`docs/circuit-import.md`
> 已确认的取舍：生成物放 **`src/generated/`**（可读可 diff）；参数格式化只支持
> `percent / db / plain / enum`；**Windows / Linux 已落地，standalone 单列**，且按平台**可插拔**。

---

## 1. 目标

插件项目的"声明"只有两份数据：

1. `rustomp.toml`（身份 / 参数 / 界面 / 构建目标）
2. `<project>/circuit/`（电路实现，手写 Rust）

其余全部由工具生成或由后端执行：

```
rustomp.toml ──┬─► rustomp gen ──► <project>/plugin/src/generated/*.rs   (样板代码)
               └─► rustomp pack ─► 各平台产物 (.au/.vst3/.clap/.exe/安装包)
```

手写保留：`Circuit` 实现、自定义 GUI 控件、自定义持久化状态、MIDI。

## 2. 现状与待补齐的四类声明

| 类别 | 现在 | 目标 | 阶段 |
|---|---|---|---|
| **A 身份/元数据** | `[plugin]/[au]` → `OUT_DIR/identity.rs` | 迁到 `src/generated/identity.rs` | S1 |

## 3. 代码生成

### 3.1 形态与位置

生成到 **`<project>/plugin/src/generated/`**（**入库**），由 `rustomp-gen` 写出：

```
src/generated/
  mod.rs            // 模块汇总
  identity.rs       // 名字 / CLAP id / 三套 VST3 id（变体用 cfg 选择，文件静态）
  params.rs         // PluginParams 结构体 + Default + to_dsp()
  plugin_impl.rs    // Plugin / ClapPlugin / Vst3Plugin impl + 导出宏 + 界面钩子
```

命令：

```bash
cargo run -q -p rustomp-gen -- <项目目录>            # 生成
cargo run -q -p rustomp-gen -- <项目目录> --check    # 只比对（CI 防漂移）
```

> **`identity.rs` 不再由 build.rs 生成**（S1c）：变体差异改成 `#[cfg(feature = "mono"/"stereo")]`，
> 于是文件是静态的、可入库、可 diff、可 `--check`。`build.rs` 已移除（GUI 阶段也不再加回来）。
>
> **界面（S1d，已实现）**：`panel.rs`（`[ui]` → `PanelSpec`）与 `bridge.rs`（`[[params]]` → `ParamAccess`）
> 都由 `rustomp-gen` 生成；`editor.rs` 里只剩"创建 egui 编辑器"几十行。
> `plugin_meta.py --panel-rust` 已退役（保留一行报错，防止旧脚本产出第二份）。
>
> 历史上的说明：`panel.rs` 与 egui 依赖在 `gui` feature 之后。
>
> **素材**：`[assets]` 里的 PNG 由生成器写成 `generated/assets.rs`（`PANEL_PNG` + `IMAGES`），
> 手写的 `editor.rs` 不再出现 `include_bytes!`。生成前会检查素材文件是否存在。
> `plugin_impl.rs` 里已经留好钩子 —— `gui` 关闭时 `editor()` 返回 `None`；
> 开启时调用手写的 `src/editor.rs::make(params, activity)`。生成器不掺和 GUI。

规则：

- **头部带 `// @generated by rustomp gen — do not edit`**，文件内容确定性（同 manifest 同输出）；
- 手改一律放到同目录的 `local.rs`（人工维护，`mod.rs` 里 `pub mod local;`）；
- `rustomp gen --check` 只比对不写入，CI 用它防漂移。

### 3.2 生成内容

`params.rs`（由 `[[params]]` 生成）：

```rust
#[derive(Params)]
pub struct Params {
    #[id = "gain"]  pub gain: FloatParam,
    #[id = "mode"]  pub mode: BoolParam,
    #[persist = "editor-state"] pub editor_state: Arc<EguiState>,
}
impl Default for Params { /* range/format/smoothing 来自 manifest */ }
impl rustomp_gui::ParamAccess for Access<'_> { /* get/set 的 match 由参数表生成 */ }
```

`plugin_impl.rs`：`Plugin`（含 `process` 的样板循环）、`ClapPlugin`、`Vst3Plugin`、`nih_export_*!`。
生成器**不懂 DSP**：`process` 只是"读参数 → `Engine<C>::set_params` → `process` → 写活动量"。

### 3.3 参数的表达力（已定）

`type = "float" | "bool"`，`format = "percent" | "db" | "plain" | "enum"`。
**参数值一律是"电位器位置 0..1"**，taper（A/B/C）在电路里换算 —— UI、自动化、DSP 语义一致。

### 3.4 电路侧：网表 → MNA 装配代码（S1a/S1b，已实现）

与上面的"身份/参数"生成并列，另有一条**电路侧**生成：

```bash
cargo run -q -p rustomp-import -- <网表.cir> --mna <输出.rs> [--check]
```

| 步骤 | 规则 |
|---|---|
| 解析 | `R C L D V I Q J M X` + `.model`（只记名字）+ `.subckt/.ends`（整段跳过） |
| 导线合并 | 阻值 ≤ 0.01 Ω 视为理想导线，两端节点并成一个（面包板连接线的典型形态） |
| 节点编号 | 地 = 0，其余按**名字排序**（保证生成物 diff 稳定） |
| 模型映射 | **闭集**：命中库内型号才生成；未命中报错并列出现有型号（ADR-013） |
| 激励 | 纯 DC 源 → `fix_node`（不占未知量）；`SIN/AC/PULSE` 源 → **输入端口** |
| 输出端口 | `* @rustomp in=<源名> out=<节点名>` 指令 |
| **参数化（S1b）** | `param <元素> <字段> pot max=<r> [invert]`、`switch <字段> <a> <b> closed=/open=` |
| 产物 | 节点常量 + `build(fs, &Params)` + `Params` + **`impl rustomp_dsp::Circuit`**（`set_params` 只改电阻值） |

产物入库（`<project>/.../generated/*.rs`），并配**漂移守卫**测试：重新生成与仓库内容逐行比较。
`--check` 只比对不写入，可直接进 CI。

**参数化（S1b）**：网表注释里的指令

```text
* @rustomp in=VS1 out=n_t27R
* @rustomp param RP1A gain pot max=500k              # R = max·gain
* @rustomp param RP2B level pot max=500k invert      # R = max·(1−level)
* @rustomp switch symmetric n_t10L n_t5L closed=0.001 open=1e12
```

会生成 `Params` 结构体 + `impl rustomp_dsp::Circuit` 的 `Ckt`（`set_params` 只改电阻值）。

生成物必须在**行为层**验证（DC 工作点 + THD），不能只比文本 ——
E44 里有一个"编译通过、不报错、但音频被送进电源轨"的例子；
E45 里还有一条"直流工作点被压摆率限制污染、开场凭空多出瞬态"（离线稳态测试看不见）。

### 3.5 平台代码片段（可插拔的代码生成侧）

生成器有一个 `PlatformCodegen` 钩子，按宿主平台选择片段（可空）：

| 平台 | 片段内容 |
|---|---|
| macOS | 通常为空（AU 相关全在打包侧） |
| Windows | standalone 用 `#![cfg_attr(windows, windows_subsystem = "windows")]` 等 |
| Linux | standalone 的 .desktop / 图标元数据（打包侧消费） |

片段只允许**追加少量 cfg 守卫的代码**，不允许改变核心 impl 的形态 —— 否则跨平台行为会分叉。

### 3.6 与外部设计器的接口（首选设计器已就位）

原理图用 **rustomp-circuit-designer**（首选），面板用单独的 GUI 设计器；
本项目只保证两侧的契约，不实现设计器本身。

```text
 rustomp-circuit-designer ──(.design.json 工程 / .cir 网表 + @rustomp 指令)──┐
                                                                              ├─► rustomp-import --mna ──► <project>/src/generated/circuit.rs
 breadspice（次选）──────────(.bread)───────────────────────────────────────┘                                   │
 面板设计器 ──(rustomp.toml [ui] + PNG 素材)──► plugin_meta.py ──► panel.rs ─────────────────────────────────┴─► 插件 crate
```

对两侧的要求：

| 契约 | 原因 |
|---|---|
| 端口显式标注（`in=` / `out=`） | 绝不猜"哪个节点是输出"；`in=` 可写节点名（设计器写法） |
| 可调元件显式声明（`param`） | 不从 `250k + 250k` 反推电位器；元素名写网表元件名（`RP1A`） |
| 型号必须落在闭集表 | 未命中在导入阶段就报错，而不是上线后才发现替换了器件 |
| 生成物入库 + 漂移检查 | 设计器改动必须走"重新生成 → 代码评审"这条路 |

**为什么设计器不直接生成 Rust**：网表是**可被 ngspice 验证**的中间格式（对拍全靠它）；
设计器一旦直接产出代码，对拍链就断了。所以设计器只负责"画图 → 工程/网表 + 指令"。

> 2026-10-27 起，设计器的**工程文件 `.design.json` 可直接导入**（`CircuitDesigner` 导入器）；
> 它运行时读设计器的 `symbols/symbols.json` 拿引脚几何，并与设计器导出的 `.cir` **逐行对拍**。

## 4.0 平台策略：打包分仓 + 外部工具（ADR-015）

**本仓库不做任何平台打包。** 三个平台各自一个**独立仓库**（都已落地），开发者按需拉取接进工作流：

```text
rustomp（框架 + 平台契约）
   ├── rustomp-mac-plugin     macOS：AU / VST3 / CLAP（universal）        ✅ v0.1.7
   ├── rustomp-win-plugin     Windows：VST3 / CLAP（x64/arm64）+ MSI     ✅ v0.3.0
   └── rustomp-linux-plugin   Linux：VST3 / CLAP + tar.gz                ✅ v0.1.0
```

| 层 | 谁提供 | 状态 |
|---|---|---|
| DSP / 电路 / 器件 / 代码生成 | 本仓库 | ✅ 纯 Rust，三平台都能编 |
| macOS 打包（AU/VST3/CLAP） | `rustomp-mac-plugin`（本仓 `scripts/build-all.sh` 是瘦包装） | ✅ 已在 Logic 实机验证 |
| Windows 打包（VST3/CLAP + MSI） | `rustomp-win-plugin` | ✅ 已在本机 DAW 实测出声 |
| Linux 打包（VST3/CLAP + tar.gz） | `rustomp-linux-plugin` | ✅ x64 实测；arm64 / 容器 / GUI / 真实宿主待验 |

**外部打包工具要满足的契约**（与 §4.2 一致）：

1. 入口：`pack.sh <plugin_dir> --variant … --format …`，成功时在 stdout 逐行打印 `ARTIFACT: <路径>`；
   （早期草图的 `scripts/pack/<platform>/<format>.sh` 未被采用：三个平台都用 `pack.sh` + 参数，
   理由见 `rustomp-win-plugin` 的 W-008：stdout 只允许 `ARTIFACT:`，其余全走 stderr）
2. 只消费 `<plugin_dir>/rustomp.toml` 与已生成的 `src/generated/`，**不改 DSP/电路/生成物**；
3. 能力声明（支持哪些格式/变体）写在它自己的 README 与 `capabilities.toml` 里；
4. 验证标准：能在目标宿主上安装、扫出预期身份、渲染正常。

> 框架侧只有**一个**入口：`scripts/build-all.sh` 按平台分派到对应的 `pack.sh`
> （`RUSTOMP_PACKER` 可覆盖），只透传 `ARTIFACT:`；新平台 = 实现一个 `pack.sh` + 在分派里加一行。
> 工具本身只读 `[plugin] [au] [build]` 与 `[requires] packer`。

> 仓库边界、文件归属、版本约束与拆分顺序见 **`docs/ecosystem.md`**。
>
> 为什么不在本仓库做条件编译：难点不是编译而是**打包与宿主兼容**（clap-wrapper/CMake/签名/宿主缓存），
> 每个平台都必须在本机验证过才算数。详见 DEVLOG ADR-015。

## 4. 打包后端（可插拔的平台侧）

### 4.1 两个平面

| 平面 | 在哪运行 | 产物 |
|---|---|---|
| **代码生成** | 任意主机（确定性） | `src/generated/*.rs` |
| **打包** | **各自平台本地**（需要该平台工具链/签名） | 发布产物 |

> **不推荐从 macOS 交叉编译 Windows/Linux**：VST3 SDK 需要 MSVC、GUI 需要 X11/Wayland 头文件、
> 签名工具各平台不同。正确做法是 **CI 矩阵**（见 §6）。Windows 工具就是这么落的：
> 在**真实 Windows 机器**（MSVC + MSYS2）上开发、打包、用 DAW 出声，而不是在 macOS 上猜。

### 4.2 后端契约

每个「平台」提供一个可执行入口 `pack.sh`（按 `--format` 分派到各格式）：

```
pack.sh <plugin_dir> [--variant mono|stereo|dual] [--format …] [--arch …] [--no-install]
```

> 早期草图是「每个「平台 × 格式」一个脚本」（`scripts/pack/<platform>/<format>.sh`）；
> 三个已落地的工具都没采用它：共用一套体检/读清单/构建逻辑，用 `--format` 分派更少重复。
> 实际入口的契约见 `rustomp-win-plugin` W-008（stdout 只允许 `ARTIFACT:`）与
> `rustomp-mac-plugin` 的 `pack.sh`。

环境变量（只增不改，保持向后兼容）：

| 变量 | 含义 |
|---|---|
| `PLUGIN_DIR` | 插件项目目录 |
| `VARIANT` | `mono` / `stereo` / `dual` |
| `TARGET_TRIPLE` | 例如 `aarch64-apple-darwin`、`x86_64-pc-windows-msvc` |
| `PROFILE` | `release` / `debug` |
| `OUT_DIR` | 产物输出目录 |
| `SIGN_MODE` | `none` / `adhoc` / `developer-id` |

约定：

1. **幂等**：重复执行不产生重复产物；
2. **失败非零退出**，错误信息写 stderr；
3. 成功时向 stdout 打印 `ARTIFACT: <路径>`（每产物一行），由驱动收集；
4. 从 `src/generated/identity.rs` 与 `rustomp.toml` 读取身份，**不得自行硬编码**。

### 4.3 后端能力声明

每个后端附带一份能力描述（`scripts/pack/<platform>/<format>.meta` 或 Rust 侧常量）：

```toml
platforms = ["macos"]
formats   = ["au"]
requires  = ["cmake", "clap-wrapper", "AudioUnitSDK"]
```

驱动在打包前校验「请求的 format ⊆ 平台支持」，不支持时明确报错而不是静默跳过。

### 4.4 平台矩阵（当前状态）

| 平台 | au | vst3 | clap | standalone | 安装包 |
|---|---|---|---|---|---|
| **macOS** | ✅（clap-wrapper） | ✅（nih-plug） | ✅（nih-plug） | ⬜ | ✅ **DMG**（用户级）；`pkg` ⬜ |
| **Windows** | ❌（无 AU） | ✅（`rustomp-win-plugin` v0.3.0） | ✅（同上） | ⬜ 不在范围 | ✅ **MSI ×2**（系统级 / 用户级） |
| **Linux** | ❌（无 AU） | ✅（`rustomp-linux-plugin` v0.1.0） | ✅（同上） | ⬜ 不在范围 | ✅ **tar.gz**（可复现 + `install.sh`）；deb/flatpak ⬜ |
| `au3` | ⬜ 需完整 Xcode | — | — | — | — |
| `aax` | ❌ **GPL-3 与 Avid 协议冲突**（ADR-005 / R10） | | | | |

> Windows 的两个 MSI 是**两个产品身份**（不同 `UpgradeCode`），按安装范围固定：
> 单包双范围会被 MSI 重新定价，实测出现“两处都写”（`rustomp-win-plugin` W-010）。
> 两架构 identity 相同，`--arch both` 默认只装 x64；arm64 在 x64 机器上只做静态校验。
>
> Linux 的分发包是 **tar.gz**（`--format targz`，不是 `tar.gz`）：`install.sh` 支持
> user / system / prefix / uninstall / dry-run；**产物与构建机 glibc 绑定**，
> 要兼容老发行版用 `--container`（默认 debian:12 / glibc 2.36）。

## 6. 验收方式：CI 矩阵

> 现状：框架仓 CI 只有 **macOS**；但参考插件仓 `sparklin-drive` 已有
> `.github/workflows/release.yml`：tag `v*` 触发 **macOS / Windows / Linux** 三平台构建并发布
> GitHub Release（mac DMG、win MSI、linux tar.gz），`workflow_dispatch` 可 dry-run。
> 三个打包器各自带 `doctor.sh` / `verify.sh`（Linux 另有 ELF/ldd）；打包器仓自身仍无 CI。
> 下面矩阵是目标形态，但已在一个真实插件上跑通（DEVLOG E100）。

```yaml
strategy:
  matrix:
    os: [macos-14, windows-2022, ubuntu-22.04]
steps:
  - ./scripts/new-plugin.sh "CI Demo"        # 生成一个同构项目
  - rustomp gen --check                       # 生成物与 manifest 一致
  - cargo build --release -p ci-demo         # 能编译
  - rustomp pack --formats <平台支持的集合>   # 走该平台的后端
  - 校验 ARTIFACT 行里的路径存在
```

**这就是"可插拔"的验收**：新增平台 = 加一个 `scripts/pack/<platform>/` 目录 + CI 矩阵加一行。

## 7. 平台细节与风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| Windows 需要 MSVC | VST3 SDK 是 C++，需 `cl.exe`；`vst3-sys` 由 cargo 编译 | Windows runner 原生构建，不交叉 |
| Linux 的 GUI 依赖 | egui-baseview 需要 X11 / Wayland 头文件 | CI `apt install libx11-dev libxkbcommon-dev` 等；文档写明 |
| 签名/公证各平台不同 | macOS Developer ID + notarytool；Windows Authenticode；Linux 无 | `SIGN_MODE` 抽象；M4 再补 |
| AU 工具仅 macOS | `auval`、`au-smoke`、`clap-wrapper` | 后端能力声明里标 `platforms = ["macos"]` |
| 环境覆盖不全（无 ARM 机器 / Linux 的容器与 GUI 未跑通） | 只能靠 CI + 用户验证 | Windows x64 已在真机完成打包 + DAW 实测；Linux x64 已在真机完成构建/验证/tar.gz（2026-10-29）；arm64、Linux 容器与 GUI 插件仍待验证 |
| 生成物与 nih-plug 版本耦合 | 生成代码依赖 nih-plug API（固定 rev） | 生成物保持小；升级 rev 时重生成并 diff |
| 生成物入库与手改冲突 | 有人直接改 `generated/*.rs` | `gen --check` 检测；手改放 `local.rs` |
